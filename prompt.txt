How Zero-Downtime Bots Work
There are three main ways developers achieve this in Python, ranging from simplest to most robust:

1. Dynamic Module Reloading (Hot Reloading)
Instead of putting 40k lines in one massive script, the bot is broken into a tiny "core" script and dozens of "plugin" scripts (e.g., blackjack.py, slots.py, wallet.py). The core script stays running forever. When a developer updates slots.py, they send a secret admin command to the bot (like /reload slots). The bot uses Python's importlib.reload() to dynamically swap the old code for the new code in memory without restarting the actual process.

2. The Webhook & Reverse Proxy Method (Blue-Green Deployment)
Instead of the bot constantly asking Telegram for updates (Long Polling), Telegram pushes updates to a web URL via Webhooks.

How it works: You put a web server like Nginx in front of your bot. Version A of your bot is running on Port 8000.

The Update: You start Version B of your bot in the background on Port 8001. Once Version B is fully loaded and ready, you instantly tell Nginx to route all new Telegram messages to Port 8001. Then, you safely shut down Version A. The users never notice a thing.

3. Decoupled Architecture (Message Queues)
This is how enterprise-grade bots do it. The system is split in two:

The Receiver: A tiny, dumb script whose only job is to receive messages from Telegram and instantly push them into a queue (like Redis or RabbitMQ).

The Workers: Your heavy 40k-line casino logic runs in separate "worker" processes that pull messages from the queue.

The Update: You can kill all the workers, update the code, and restart them. The Receiver never stops running, so Telegram messages just pile up safely in the queue for a few seconds. When the new workers boot up, they instantly process the backlog. No messages are lost.
